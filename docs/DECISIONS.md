## D1. Стек: один Node-сервер + SQLite + SSE, фронт React + Vite + Tailwind — ✅ (Егор, 7.09.2026)

**Что решили.**
- Один процесс Node.js: веб-сервер **Hono** (маленький, TypeScript, без магии), база **SQLite** (файл `data/arena.db`, библиотека `better-sqlite3`), реалтайм через **SSE** (Server-Sent Events — встроено в браузер, само переподключается).
- Фронтенд: **React + Vite + Tailwind**, TypeScript. Одна сборка, сервер раздаёт готовые файлы.
- **Демо и репетиции — бесплатно, на Маке Егора** (см. D14). Платный хостинг (Railway, ~$5/мес) подключаем позже, когда демо принято.
- **План Б без интернета:** тот же код на ноутбуке в зале, зрители подключаются к своему роутеру. Егор подтвердил, что роутер и ноутбук в зале поставить можно (Q7).

**Почему не вариант из ТЗ (Next.js + Supabase + Vercel).**
| | Вариант ТЗ (Next.js + Supabase + Vercel) | Принятый (Node + SQLite + SSE) |
|---|---|---|
| Сколько сервисов настраивать | три: Vercel, Supabase, GitHub | два: Railway, GitHub (для демо — ноль) |
| Атомарность бюджета | SQL-функции в Postgres + RLS-политики, легко ошибиться | SQLite пишет строго по одному, гонки невозможны по конструкции |
| Реалтайм | Supabase Realtime, лимит 200 соединений на бесплатном тарифе | SSE в том же процессе, лимит — тысячи |
| Задержки | serverless «холодные старты» на Vercel | процесс живёт постоянно |
| Риск «уснувшей» базы | бесплатный проект Supabase засыпает через 7 дней без активности | нет |
| Цена | бесплатно | ~$5/мес за хостинг, демо бесплатно |
| Работа без интернета в зале | невозможна | тот же код на ноутбуке + свой роутер |
| Локальная репетиция | нужен доступ к облачной базе | `npm run dev`, всё на Маке |

## D2. Клиент присылает целевую сумму, а не дельту — ✅

ТЗ: «клиент присылает изменить вложение на дельту D». Проблема: при плохой связи клиент повторяет запрос. Если первый запрос дошёл, а ответ потерялся, повтор дельты **применится дважды**.

Решение: клиент присылает **«поставить моё вложение в проект X равным S»**. Повтор такого запроса безвреден. Сервер проверяет: S ≥ 0, сумма по всем проектам ≤ бюджет, голосование открыто, проект открыт — и возвращает полное состояние зрителя. Клиент держит одну очередь запросов (не более одного в полёте), новые нажатия сливаются в последнее целевое значение.

## D3. `/screen` и `/screen/results` закрыты паролем оператора — ✅

ТЗ не защищает экран. Но на нём — общие суммы, которые зрителям видеть нельзя. Любой зритель, угадавший адрес `/screen`, увидит лидера. Решение: экран открывается только с той же cookie, что и админка (оператор логинится на ноутбуке один раз).

## D4. «Отвязать билет» = передача гостя новому устройству, а не удаление — ✅

Сценарий: зритель потерял доступ (сменил телефон, почистил браузер). Ведущий нажимает «отвязать». Следующий, кто введёт этот номер билета, **получает того же гостя с его деньгами и вложениями**; старый токен перестаёт работать. Вложения не пропадают, бюджет не удваивается.

---

## D5. Закрытие открытого проекта удаляет вложения в него — ✅

Свободный остаток зрителя = бюджет − сумма вложений. Поэтому «вернуть деньги» = удалить строки вложений в этот проект. Действие пишется в лог с суммами, чтобы можно было разобраться. В админке — подтверждение с текстом «Вложения N зрителей на сумму M будут возвращены».

---

## D6. Реалтайм: SSE-сигнал «обновись» + страховочный опрос — ✅

SSE передаёт не данные, а **сигнал** с номером версии: «состояние шоу изменилось». Клиент после сигнала перезапрашивает свой обычный эндпоинт. Плюс страховочный опрос раз в 5 секунд, если SSE молчит. Два канала сигналов:
- `show` — открыли/закрыли проект, голосование, регистрацию, сменили режим экрана, показали итоги зрителям. Слушают все.
- `totals` — кто-то переложил деньги. Слушают только экран и админка. Сигнал не чаще раза в секунду.

Зрители **не** получают сигнал на чужие вложения — иначе каждое нажатие в зале вызывало бы 150 перезапросов.

## D7. Одна форма данных для зрителя — ✅

## D11. Итоги зрителям — по отдельной кнопке ведущего — 🟡

Егор хочет, чтобы после закрытия голосования зритель видел список лидеров, общие суммы и свои вложения (Q10). Делаем. Но если показать это на телефонах **в момент закрытия**, пошаговое раскрытие на большом экране теряет смысл: зал узнает победителя из телефона раньше, чем со сцены.

Предложение: в админке две кнопки. «Закрыть голосование» — кнопки у зрителей блокируются, телефон показывает «Голосование закрыто, смотрите на экран» и личный расклад. «Показать итоги зрителям» — ведущий нажимает после раскрытия победителя на экране, и на телефонах появляется полный список с общими суммами. Поле `results_visible_to_guests` в `show_state`.

Флаг `show_totals_to_guests` из ТЗ (общие суммы во время голосования) остаётся, по умолчанию выключен.

## D12. «Раскрытие суммы» на экране — снимок на момент нажатия — 🟡

Режим экрана «раскрытие»: ведущий говорит «посмотрим, сколько зал вложил в проект X», число выезжает счётчиком. Голосование при этом ещё открыто, люди продолжают перекладывать деньги. Два варианта, что делать с числом дальше:
- **Живое**: число продолжает меняться на экране. Эффектно, но ведущий скажет «полмиллиона», а через секунду там 480 000. Зал видит движение и начинает играть против экрана.
- **Снимок** (предлагается): в момент нажатия «Раскрыть» сервер запоминает сумму и число инвесторов, экран показывает этот снимок и не меняет его, пока ведущий не нажмёт «Раскрыть» снова. Предсказуемо, ведущий контролирует момент.

Не путать с финальными итогами (`/screen/results`): они после закрытия голосования, там ничего не меняется по определению.

## D13. Коды билетов генерирует система — 🟡

Списка билетов нет, но Егор может влиять на то, как создаются номера (Q3). Предложение: система сама генерирует нужное количество кодов вида `K7H3PX` — 6 символов, без похожих знаков (нет 0/O, 1/I/L). Егор выгружает список из админки одной кнопкой и отдаёт тому, кто печатает билеты или карточки на вход. Режим `whitelist`: чужой код не подобрать, лишний бюджет не набрать.

Если билеты делает площадка со своими номерами — импортируем их список текстом (как в ТЗ). Режим `free` остаётся запасным на случай, когда списка нет вообще.

## D14. Демо и репетиции — на Маке Егора, бесплатно — ✅ (Егор, 7.09.2026)

Сервер запускается на Маке командой `npm run dev`. Телефоны в той же Wi-Fi открывают адрес Мака (вида `http://192.168.x.x:3000`), QR-код ведёт туда же. Это ровно конфигурация плана Б, поэтому план Б проверяется с первого дня.

Показать демо кому-то не из дома: временная ссылка через Cloudflare Tunnel (`cloudflared`, бесплатно, без аккаунта; адрес случайный вида `xxx.trycloudflare.com`, меняется при каждом запуске). Постоянный хостинг (Railway) — на этапе 7, после приёмки демо.

## D15. Адрес для QR — 🟡

QR Егор делает сам. Нужен «приличный» адрес. Бесплатных и одновременно приличных почти нет, варианты по убыванию приличности:
1. **Свой домен, если уже есть** (от любого прошлого сайта): поддомен `arena.твой-домен.ru` — бесплатно, выглядит лучше всего.
2. **Купить дешёвый домен**: `.ru` — 200–400 ₽ в год (reg.ru, nic.ru), `.site`/`.online`/`.fun` — 100–200 ₽ первый год (Namecheap, Porkbun). DNS — бесплатно на Cloudflare. Пример: `unicorn-arena.ru`.
3. **Адрес хостинга**: `arena-edinorogov.up.railway.app` — бесплатно вместе с хостингом, прилично, но длинно для набора руками.
4. Бесплатные поддомены (`duckdns.org`, `mooo.com`) — выглядят хуже варианта 3, не советую.

Для демо на Маке адрес — IP-адрес в локальной сети; на него QR тоже работает.
