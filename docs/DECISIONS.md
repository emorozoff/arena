## D1. Стек: один Node-сервер + SQLite + SSE, фронт React + Vite + Tailwind — ✅ (Егор, 7.09.2026)

**Что решили.**
- Один процесс Node.js: веб-сервер **Hono** (маленький, TypeScript, без магии), база **SQLite** (файл `data/arena.db`, библиотека `better-sqlite3`), реалтайм через **SSE** (Server-Sent Events — встроено в браузер, само переподключается).
- Фронтенд: **React + Vite + Tailwind**, TypeScript. Одна сборка, сервер раздаёт готовые файлы.
- **Демо и репетиции — бесплатно, на Маке Егора** (см. D14). Платный хостинг (Railway, ~$5/мес) подключаем позже, когда демо принято.
- **План Б без интернета:** тот же код на ноутбуке в зале, зрители подключаются к своему роутеру. Егор подтвердил, что роутер и ноутбук в зале поставить можно (Q7).

**Почему не вариант из ТЗ (Next.js + Supabase + Vercel).**
| | Вариант ТЗ (Next.js + Supabase + Vercel) | Принятый (Node + SQLite + SSE) |
|---|---|---|
| Сколько сервисов настраивать | три: Vercel, Supabase, GitHub | два: Railway, GitHub (для демо — ноль) |
| Атомарность бюджета | SQL-функции в Postgres + RLS-политики, легко ошибиться | SQLite пишет строго по одному, гонки невозможны по конструкции |
| Реалтайм | Supabase Realtime, лимит 200 соединений на бесплатном тарифе | SSE в том же процессе, лимит — тысячи |
| Задержки | serverless «холодные старты» на Vercel | процесс живёт постоянно |
| Риск «уснувшей» базы | бесплатный проект Supabase засыпает через 7 дней без активности | нет |
| Цена | бесплатно | ~$5/мес за хостинг, демо бесплатно |
| Работа без интернета в зале | невозможна | тот же код на ноутбуке + свой роутер |
| Локальная репетиция | нужен доступ к облачной базе | `npm run dev`, всё на Маке |

## D2. Клиент присылает целевую сумму, а не дельту — ✅

ТЗ: «клиент присылает изменить вложение на дельту D». Проблема: при плохой связи клиент повторяет запрос. Если первый запрос дошёл, а ответ потерялся, повтор дельты **применится дважды**.

Решение: клиент присылает **«поставить моё вложение в проект X равным S»**. Повтор такого запроса безвреден. Сервер проверяет: S ≥ 0, сумма по всем проектам ≤ бюджет, голосование открыто, проект открыт — и возвращает полное состояние зрителя. Клиент держит одну очередь запросов (не более одного в полёте), новые нажатия сливаются в последнее целевое значение.

## D5. Закрытие открытого проекта удаляет вложения в него — ✅

Свободный остаток зрителя = бюджет − сумма вложений. Поэтому «вернуть деньги» = удалить строки вложений в этот проект. Действие пишется в лог с суммами, чтобы можно было разобраться. В админке — подтверждение с текстом «Вложения N зрителей на сумму M будут возвращены».

## D6. Реалтайм: SSE-сигнал «обновись» + страховочный опрос — ✅

SSE передаёт не данные, а **сигнал** с номером версии: «состояние шоу изменилось». Клиент после сигнала перезапрашивает свой обычный эндпоинт. Плюс страховочный опрос раз в 5 секунд, если SSE молчит. Два канала сигналов:
- `show` — открыли/закрыли проект, голосование, регистрацию, сменили режим экрана. Слушают все.
- `totals` — кто-то переложил деньги. Слушают только экран и админка. Сигнал не чаще раза в секунду.

Зрители **не** получают сигнал на чужие вложения — иначе каждое нажатие в зале вызывало бы 150 перезапросов.

## D12. «Раскрытие суммы» на экране — живое число — ✅ (Егор, 7.09.2026)

Режим экрана «раскрытие»: ведущий выбирает проект, число выезжает счётчиком до текущей суммы и **дальше продолжает меняться живьём**, пока люди перекладывают деньги. Зал видит движение и играет против экрана — это осознанный выбор Егора ради драматургии.

Как делаем: экран получает свежие суммы не чаще раза в секунду (D6), число плавно докручивается от старого значения к новому, а не прыгает. Никаких снимков в базе не храним — на экране всегда текущее значение.

Отвергнуто: снимок на момент нажатия «Раскрыть».

## D13. Коды билетов генерирует система, формат простой; окончательно — после демо — 🟡 (частично, Егор 7.09.2026)

Что решено: билеты делает наша система (не площадка), номера должны быть **простыми, чтобы легко вписать с телефона**. Людей 100–200. Точный вид номеров Егор выберет после демо.

Предложение на выбор (обсудим после демо):
- **4 цифры**, например `4817`. На телефоне открывается цифровая клавиатура, вписать за две секунды. Всего 9 000 вариантов, из них валидных 200 — случайно угадать чужой почти невозможно, а после закрытия регистрации и вовсе. Рекомендуется.
- **3 цифры** (`481`) — ещё проще, но 900 вариантов на 200 билетов: каждый пятый случайный набор попадёт в чужой билет. Не советую.
- **Номер ряда и места** (`7-12`) — если билеты именные с местами. Удобно, но легко угадать соседа.

Генерация: админка → «Сгенерировать N кодов» → случайные, без повторов и без «красивых» последовательностей → «Скачать список» текстом. Режим `whitelist`. Импорт чужого списка и режим `free` остаются как запасные. В демо для примера используем 4 цифры.

## D16. Демо для заказчика — прототип по ссылке на GitHub Pages (+ тот же файл) — 🟡

Егору нужно показать демо заказчику так, чтобы оно открывалось с телефона по ссылке. Настоящая система требует сервер, поэтому прототип живёт целиком внутри одной страницы.

Как: **интерфейс делаем один раз**, а «сервер за кулисами» к нему подключаем два разных:
- **Игрушечный сервер внутри страницы** (`web/src/lib/api.mock.ts`): хранит всё в памяти браузера, изображает зал из ~100 зрителей, которые сами двигают деньги, чтобы экран «жил». Наверху переключатель ролей: Зритель / Ведущий / Экран. На странице написано, что данные ненастоящие.
- **Настоящий сервер** (`web/src/lib/api.ts` → Node + SQLite) — для репетиций и шоу. Интерфейс тот же, до пикселя.

Где живёт прототип: репозиторий `github.com/emorozoff/arena` (публичный, подключён 7.09.2026), **GitHub Pages** по адресу `https://emorozoff.github.io/arena/`. Публикация автоматическая из ветки **`demo`** (GitHub Actions). Разработка идёт в `main` и на демку не влияет: заказчик видит стабильную версию, пока Егор не скажет обновить (тогда `main` вливается в `demo`). Тот же прототип собирается и в один файл `demo/arena-demo.html` на случай, если нужно отправить файлом.

Отвергнуто: отдельный одноразовый макет (работа выбрасывается); показывать настоящий сервер через туннель с Мака (Мак должен быть включён).

## D21. Финал с поочерёдным раскрытием — из пульта, на том же экране — ✅ (Егор, 7.09.2026)

Егор описал финал: ведущий показывает места по одному, начиная с последнего; каждый следующий с большей суммой встаёт сверху; победитель последним. Без нумерации и без строк-заглушек «???».

Как сделано:
- Ведущий нажимает «Закрыть голосование». Экран в режиме «Общий расклад» очищается, остаётся заголовок «Итоги голосования».
- В пульте появляется блок «Финал» (только пока голосование закрыто): «Показать следующего», счётчик «Показано N из M», «Скрыть всех», «Показать всех». Нажатие «Показать следующего» заодно переключает экран на общий расклад, чтобы ведущему не делать два действия.
- Поле `revealed_count` в состоянии шоу. Сервер отдаёт экрану **только показанные места** (последние N строк рейтинга), непоказанные на экран не попадают. Смена состояния голосования сбрасывает счётчик в 0.
- Победитель появляется последним, с лёгкой пометкой: маленькая подпись «Победитель» и тонкая рамка, размер и цвет строки не меняются.

Отвергнуто: отдельная страница итогов с управлением клавишами (D19, раздел 8 ТЗ) — ведущий управляет финалом с телефона.

## D23. Кто есть кто на настоящем сервере: токен зрителя и сессия ведущего — ✅

- **Зритель.** При входе сервер выдаёт токен устройства: кладёт его в cookie `guest_token` и возвращает в ответе; страница сохраняет его в localStorage и шлёт заголовком `x-guest-token`. Сервер принимает любой из двух. Так вход переживает и чистку cookie в браузере внутри Telegram, и блокировку localStorage в приватном режиме.
- **Ведущий.** Пароль из `.env` (`ADMIN_PASSWORD`). После входа — случайный id сессии в cookie `admin_session` и в таблице `admin_sessions` (живёт сутки, переживает перезапуск сервера). Пароль сравнивается за постоянное время.
- **Экран** пользуется той же сессией ведущего (D3): без неё страница экрана показывает форму пароля, а не пустоту.
- В `.env` файл не входит в git; пример — `.env.example`.

## D24. Расчёт на 800 зрителей — 🟡 (новость от Егора, 10.09.2026)

Заказчик ожидает до 800 человек вместо 100–150. Что это меняет:
- **Сервер.** Один процесс Node + SQLite справляется: 800 одновременных SSE-соединений и всплеск в 800 запросов «обновись» после каждого «Открыть проект» — это доли секунды работы для базы. Но нужен запас: **2 vCPU, 4 ГБ памяти**, диск от 20 ГБ, канал от 100 Мбит/с. И обязательно поднять лимит открытых файлов (systemd `LimitNOFILE=65536`), иначе Linux по умолчанию не даст больше ~1000 соединений.
- **Страховочный опрос.** 800 телефонов, опрашивающих сервер каждые 5 секунд, дают 160 запросов в секунду постоянно. Пока реалтайм-соединение живо, опрос делаем реже (раз в 15 секунд), а каждые 5 секунд — только когда соединение оборвалось. Правится в `useLive.ts` и `config.ts` на этапе 6.
- **Нагрузочный тест (этап 6)** — на 1000 виртуальных зрителей, не на 150.
- **План Б (свой роутер в зале) на 800 человек не работает.** Бытовой роутер держит 50–100 устройств. Либо профессиональный Wi-Fi площадки, либо зрители сидят на мобильном интернете — тогда сервер в облаке обязателен, и главный риск вечера — сотовая сеть в зале, а не наш код. Это надо обсудить с площадкой заранее.
- **Коды билетов (D13).** 800 четырёхзначных кодов из 9 000 возможных: каждый одиннадцатый случайный набор попадёт в чужой билет. Для 800 человек лучше **5 цифр** (90 000 вариантов) — по-прежнему легко вписать.
- **Регистрация.** 800 человек регистрируются в первые минуты — всплеск в сотни входов в минуту, для сервера это немного, но QR-код должен быть виден с любого места зала: показывать его и на экране, и на распечатках у входа.

## D25. Билеты: 12-значный штрихкод с билета площадки + запас сгенерированных кодов + сектор билета — ✅ (сделано 11.09.2026)

Заказчик прислал выгрузку площадки (`Id билета`, `Сектор`, `Штрихкод`): 307 билетов, штрихкод — 12 цифр, уникальные. Зритель вводит эти 12 цифр с билета (под штрихкодом они напечатаны). Распознавание штрихкода из картинки отвергнуто (ненадёжно в зале, см. переписку 11.09).

Как делаем:
- Режим билетов `whitelist`. Формат номера: **12 цифр** (`config.ticketLength = 12`). Генерируемые в пульте запасные коды тоже 12 цифр, чтобы кассовые карточки выглядели как обычные билеты.
- Импорт в пульте принимает вставленную колонку из Excel и целые строки выгрузки: берём из строки первое 12-значное число. Повторный импорт добавляет только новые коды, уже вошедшие зрители не трогаются.
- Порядок в день шоу: последний импорт за час до начала → сгенерировать ~30 запасных кодов → распечатать → закрыть регистрацию после начала.
- Поле ввода: цифровая клавиатура, 12 знаков группами по 4 для читаемости (`7866 0018 2909`), пробелы игнорируются.
- Риск: 12 цифр вводятся дольше и с опечатками; ошибка «Билет не найден» подсказывает «проверьте цифры под штрихкодом».
- **Сектор билета** (GOLD, PLATINUM, BUSINESS, STANDARD, ПОЧЕТНЫЙ ГОСТЬ) сохраняется при импорте (колонка `tickets.sector`), показывается зрителю пометкой под названием шоу и в списке билетов пульта. Названия для показа — `config.sectorLabels`. Задел на будущее: разный бюджет по сектору (заказчик обсуждает). У сгенерированных кассовых кодов сектора нет.
